# Сверка с Shlink

Здесь лежит эталон — ответы **настоящего Shlink 5.1.8** на запросы из раздела «Контракт
совместимости с Shlink» (`CLAUDE.md` проекта) — и прогон, который сравнивает с этим эталоном любой
сервер. Задача прогона: показать, где `tiny` отвечает не так, как Shlink.

Сейчас в наборе **54 сценария, 307 запросов**. Настоящий Shlink проходит их на 100%, в том числе
повторно на том же стенде.

Отдельный модуль (`github.com/rendau/tiny/test/compat`): корневой `go test ./...` сюда не заходит.

## Быстрый старт

```bash
cd test/compat
./stand.sh up            # настоящий Shlink на localhost:18081, ключ compat-api-key
TARGET_URL=http://localhost:18081 API_KEY=compat-api-key go test -count=1 ./...
./stand.sh down          # когда больше не нужен
```

`./stand.sh reset` — снести и поднять заново (чистый Shlink), `./stand.sh status` — что запущено.

Стенд (зона «Сверка» из раздела «Тестовый стенд» в `CLAUDE.md`):

| Что | Контейнер | Порт | Доступ |
|---|---|---|---|
| Shlink 5.1.8 | `tiny-compat-shlink` | `18081` | ключ API — `compat-api-key` |
| Postgres 17 для Shlink | `tiny-compat-shlink-pg` | `54342` | `shlink` / `shlink` / `shlink` |
| Postgres 17 для tiny (`./stand.sh up-tiny`) | `tiny-compat-pg` | `54343` | `tiny` / `tiny` / `tiny` |

Shlink настроен так: `DEFAULT_DOMAIN=l.demo.test`, `IS_HTTPS_ENABLED=true`,
`DEFAULT_SHORT_CODES_LENGTH=5`, `DISABLE_TRACKING=true`, `TZ=Asia/Almaty`. Запросы идут на
`localhost:18081` с заголовком `Host: l.demo.test` или `Host: sl.demo.test`.

## Прогон против другого сервера (tiny)

```bash
./stand.sh up-tiny       # база для tiny: postgres://tiny:tiny@localhost:54343/tiny?sslmode=disable
# запустить tiny с этой базой и настройками как у Shlink на стенде:
#   DEFAULT_DOMAIN=l.demo.test  IS_HTTPS_ENABLED=true  DEFAULT_SHORT_CODES_LENGTH=5  API_KEYS=<ключ>
TARGET_URL=http://localhost:8080 API_KEY=<ключ> go test -count=1 ./...
```

| Переменная | Что это |
|---|---|
| `TARGET_URL` | адрес проверяемого сервера; не задан — сверка пропускается |
| `API_KEY` | верный ключ для заголовка `X-Api-Key` |
| `STRICT_HEADERS=1` | сравнивать строго и «мягкие» заголовки (см. ниже) |
| `COMPAT_RECORD=1` | не сравнивать, а записать ответы сервера как новый эталон |

Полезное:

- один сценарий или группа: `go test -count=1 -run 'TestCompat/redirect-' ./...`;
- заметки о «мягких» заголовках и итоговая строка видны с `-v`;
- базу между прогонами чистить не нужно: каждый прогон подставляет в адреса и свои коды случайную
  метку (`${run}`), поэтому ссылки прошлых прогонов не мешают.

Расхождение печатается так — сценарий, шаг, запрос, что ждали и что пришло:

```
сценарий create-minimal, шаг 1 «создать»: POST /rest/v3/short-urls [Host: l.demo.test]
    код ответа: ждали 200, пришло 201
    заголовок Content-Type: ждали "application/json", пришло "application/json; charset=utf-8"
    тело (JSON) отличается (- ждали, + пришло):
        …
      -   "domain": null,
      +   "domain": "",
    коротко:
      в корне другой порядок полей: ждали …, пришло …
```

Без сервера (`go test ./...` без `TARGET_URL`) идут только проверки самого прогона: что сравнение
замечает расхождения, что эталон соответствует сценариям, что стенд знает все метки из сценариев.

## Снять эталон заново

Только с настоящего Shlink и только на чистом стенде:

```bash
./stand.sh reset
COMPAT_RECORD=1 TARGET_URL=http://localhost:18081 API_KEY=compat-api-key go test -count=1 -run TestCompat ./...
TARGET_URL=http://localhost:18081 API_KEY=compat-api-key go test -count=1 ./...   # проверка: дважды подряд
TARGET_URL=http://localhost:18081 API_KEY=compat-api-key go test -count=1 ./...
```

Запись падает, если Shlink ответил `5xx` или запрос завис: такие шаги в эталон не берём (это сбои
Shlink, а не поведение, которое стоит повторять — список в «Что выяснилось»). Эталоны удалённых
сценариев и ненужные файлы тел при полной записи убираются сами.

## Как описан сценарий

Сценарии — данные в `scenarios/*.yaml`; кода на отдельный случай нет. Порядок выполнения — по
имени файла, внутри файла — как записано. Сценарий — несколько запросов подряд:

```yaml
- id: redirect-expired
  about: Срок действия ссылки истёк (validUntil в прошлом)
  steps:
    - name: создать ссылку
      create: {longUrl: "https://shop.example.invalid/${run}/expired", validUntil: "2020-01-01T00:00:00+05:00"}
      save: {code: 'shortCode =~ ^[0-9a-zA-Z]{5}$'}
    - {name: GET, path: "/${code}"}
    - {name: HEAD, method: HEAD, path: "/${code}"}
```

| Поле шага | Что значит |
|---|---|
| `method`, `path` | метод (по умолчанию `GET`) и путь с параметрами — уходит как записан |
| `host` | заголовок `Host`, по умолчанию `l.demo.test` |
| `key` | `good` — верный ключ, `bad` — неверный, `empty` — пустой заголовок; не указан — заголовка нет |
| `create` | сокращение: `POST /rest/v3/short-urls` с верным ключом и этим JSON в теле |
| `json` | тело запроса данными (уйдёт как JSON) |
| `body`, `content_type` | тело как есть (битый JSON, форма) и его тип; `content_type: none` — без заголовка |
| `headers` | прочие заголовки запроса |
| `save` | взять поле JSON-ответа в переменную: `имя: 'поле =~ выражение'`; значение обязано подходить под выражение (так проверяется длина и состав кода) |
| `mask` | заменить меняющееся поле ответа на `<имя>`: `поле: 'имя =~ выражение'` |
| `only_this_run_lines` | из текстового ответа убрать строки, подходящие под выражение, но без метки этого прогона (для `robots.txt`: там копятся ссылки прошлых прогонов) |
| `skip_body`, `only_headers` | не сравнивать тело; сравнивать только перечисленные заголовки (значок сайта) |

Подстановки в запросе: `${run}` — метка прогона (6 знаков `a-z0-9`), `${имя}` — переменная из
`save`, `${pad:N}` — набивка из N знаков (очень длинные адреса и заголовки).

Длинные адреса в сценариях ведут на `shop.example.invalid`: такого домена не существует, поэтому
Shlink не может сходить по адресу за заголовком страницы (он это делает сам, см. ниже), и поле
`title` в эталоне всегда предсказуемо.

**Метки и домены.** Каждая метка (`tags`) и каждый домен (`domain`) из сценариев должны быть
перечислены в `seed-tags.txt` и `seed-domains.txt`: стенд заводит их в Shlink заранее. Без этого
настоящий Shlink зависает (его ошибка, см. ниже). За полнотой следит тест `TestSeedCoversScenarios`.

## Что и как сравнивается

Эталон сценария — `golden/<id>.json`: по шагам запрос, код ответа, заголовки, тело. Длинные
текстовые тела (страницы 404) лежат в `golden/bodies/`.

- **Код ответа** — строго.
- **Тело.** JSON сравнивается по значениям **и по порядку полей** (как именно записаны кавычки и
  не-латинские буквы — не важно). Текст — буква в букву. Пустое тело должно быть пустым.
- **Заголовки.** Строго — все из эталона, кроме «мягких»; лишний заголовок у проверяемого сервера —
  ошибка, только если он меняет поведение клиента (`Location`, `Content-Type`, `Cache-Control`,
  `Allow`, `Access-Control-*` и подобные). «Мягкие» — `X-Request-Id`, `Content-Length`,
  `Transfer-Encoding`, `Last-Modified`, `Accept-Ranges`, `Connection`, `Server`: расхождение
  печатается как заметка и ошибкой не считается (клиенты на них не опираются; `Content-Length`
  совпал бы только при повторении JSON байт в байт). `Date` в эталон не попадает.

Правила замены меняющихся значений (все — в `runner.go`, `normalizeJSON`):

| Что в ответе | На что заменяется | Условие |
|---|---|---|
| значение переменной из `save` (случайный код) | `${имя}` | значение подошло под выражение из `save` |
| метка прогона | `${run}` | — |
| набивка | `${pad:N}` | — |
| `dateCreated` | `<now+00:00>` | дата в виде `2026-11-25T05:01:05+00:00` и не дальше 10 минут от часов прогона; смещение сохраняется — часовой пояс ответа входит в контракт |
| заголовок `X-Request-Id` | `<uuid>` | значение похоже на uuid |
| поле из `mask` (версия в `/rest/health`, текст «Cannot GET http://…!») | `<имя>` | значение подошло под выражение |

Значение, не подошедшее под своё правило, остаётся как есть — и сравнение покажет расхождение.
Если у двух переменных значение одинаковое, в ответе окажется имя той, что сохранена раньше: так
ловится случай «должна была создаться новая ссылка, а вернулась старая».

HTTP-клиент прогона (`client.go`): соединение и TLS — по 2 с, весь запрос — 15 с, до 20 соединений
на хост, по перенаправлениям не ходит (ответ `302` виден как есть), сжатие не запрашивает.

## Что выяснилось

Точное поведение Shlink 5.1.8, которое расходится с `CLAUDE.md` или там не описано. Всё, кроме
отмеченного «в эталон не вошло», зафиксировано в эталоне.

### Расходится с описанием в CLAUDE.md

1. **Даты в ответе — в UTC, со смещением `+00:00`**, а не `+05:00`, как в примере:
   `"dateCreated":"2026-11-25T05:01:05+00:00"`, а `validUntil`, присланный как
   `2099-12-05T10:01:00+05:00`, возвращается как `2099-12-05T05:01:00+00:00`. Переменная `TZ` на
   Shlink не действует; действует его собственная `TIMEZONE`. С `TIMEZONE=Asia/Almaty` даты идут
   с `+05:00`, а дата без пояса (`2099-12-05 10:01:00`) понимается как алматинская — проверено.
   Если у заменяемого Shlink задана `TIMEZONE`, эталон надо переснять
   (`SHLINK_TIMEZONE=Asia/Almaty ./stand.sh reset` и запись).
2. **Порядок полей другой:** `visitsSummary` идёт перед `hasRedirectRules`, а не после. Полный
   порядок: `shortUrl`, `shortCode`, `longUrl`, `dateCreated`, `tags`, `meta` (`validSince`,
   `validUntil`, `maxVisits`), `domain`, `title`, `crawlable`, `forwardQuery`, `visitsSummary`
   (`total`, `nonBots`, `bots`), `hasRedirectRules`.
3. **`findIfExists` сравнивает не «все остальные параметры», а только присланные.** Точное правило:
   длинный адрес совпадает буква в букву, плюс каждое из условий, если поле прислано:
   - `tags` непустой — у ссылки ровно этот набор меток (порядок не важен; меток меньше или
     больше — не подходит); `tags` не прислан или пуст — подходят любые метки;
   - `validSince`, `validUntil` — тот же момент времени (запись и пояс не важны);
   - `maxVisits` — то же число;
   - `customSlug` — тот же код;
   - `domain` — тот же домен.

   `title`, `crawlable`, `forwardQuery`, `shortCodeLength` не сравниваются вовсе. Из подходящих
   ссылок берётся **самая старая**. Если `domain` не прислан (или прислан основной), домен не
   проверяется совсем — может вернуться ссылка **второго домена**.
4. **`shortCodeLength`: нижняя граница 4, верхней нет** (7 и 20 принимаются). `0`, `1`, `3`,
   отрицательное, дробное, не число → `400`, а не длина по умолчанию. Поля нет или `null` → 5.
   Число строкой (`"6"`) принимается. При `customSlug` поле не действует.
5. **Неподдерживаемый метод — это `404`, а не `405`:** `POST`/`PUT`/`DELETE`/`OPTIONS /{код}` и
   `POST /` отдают страницу 404; `PUT`/`DELETE /rest/v3/short-urls` и `POST /rest/health` —
   `404` в виде `application/problem+json`.
6. **`robots.txt` не постоянный:** перед `Disallow: /` идут строки `Allow: /<код>` для всех ссылок
   с `crawlable=true` (со всех доменов). Без таких ссылок — только `Disallow: /`.
7. **Shlink сам ходит по длинному адресу за заголовком страницы.** Если `title` не прислан, при
   создании он делает `GET` на `longUrl` (до 3 с, до 15 перенаправлений) и кладёт в `title`
   содержимое `<title>`. Настройка `AUTO_RESOLVE_TITLES` по умолчанию включена. Проверено: адрес страницы с `<title>` дал заполненный `title`. В эталоне
   `title` без присланного значения — всегда `null` (адреса сценариев никуда не ведут).
   **Решение за ведущей сессией:** повторять ли это в `tiny`; клиентам `title` в ответе не нужен,
   а каждый запрос создания превращается в исходящий запрос наружу.
8. **`domain` принимается любой**, не только два наших: для неизвестного домена Shlink молча
   создаёт ссылку (`shortUrl` — `https://<этот домен>/<код>`).

### Переход по ссылке

- Ответ — `302` с **пустым телом** и заголовками `Location`, `Content-Length: 0`, `X-Request-Id`.
  Ни `Content-Type`, ни `Cache-Control` нет. (Стандартный `http.Redirect` в Go на `GET` пишет в
  тело ссылку и ставит `Content-Type` — это расхождение, прогон его ловит.)
- `HEAD` отвечает как `GET`: тот же код и те же заголовки. Для ненайденной ссылки `HEAD` — `404`
  с `Content-Type: text/html; charset=utf-8` и пустым телом.
- **Страниц 404 две.** «Invalid Short URL» (`golden/bodies/a974331f672f.html`, 1488 байт) — на
  любой `GET` с путём из одной части, по которому нет действующей ссылки: неизвестный код, не тот
  регистр, истёкшая, ещё не начавшаяся, а также `/.env`, `/index.php`, `/код.html`. «Not Found»
  (`golden/bodies/cb22168235ad.html`, 1428 байт) — на всё остальное: корень, путь из нескольких
  частей, косая черта в конце (`/код/`), не-`GET` методы. Обе — `text/html; charset=utf-8`.
- **Склейка параметров** (при `forwardQuery=true`): параметры длинного адреса идут первыми в своём
  порядке, новые дописываются в конец; если ключ уже есть в длинном адресе — значение заменяется на
  месте (в том числе на пустое `b=` и на ключ без значения `c`); ключ, повторённый в запросе,
  остаётся повторённым (`a=9&a=10`); если в длинном адресе ключ был дважды, а пришёл один раз —
  остаётся один. Якорь (`#frag`) остаётся в самом конце. При `forwardQuery=false` параметры
  запроса отбрасываются.
- **Кодирование `Location`:** кириллица и пробелы длинного адреса кодируются процентами (в пути,
  параметрах и якоре), уже закодированное не трогается; `+` в параметрах превращается в `%20`,
  `%2B` остаётся; `=` внутри значения — `%3D`; `[]` в ключе — `%5B%5D`; одинокий `?` пропадает.
- Ссылка основного домена открывается на любом `Host` — и на втором домене, и на постороннем, и по
  имени `shlink`. Ссылка второго домена — только на нём. Один код может существовать на двух
  доменах сразу — это две разные ссылки; на постороннем `Host` открывается ссылка основного.
- Длинный адрес не обязан быть `http`: `tg://resolve?domain=…` уходит в `Location` как есть.
- `maxVisits` не срабатывает: три перехода подряд по ссылке с `maxVisits=1` — три раза `302`.
- В эталон не вошло: `GET /{код}/track` — Shlink отдаёт картинку-пиксель 1×1 (`200`, `image/gif`).

### Создание ссылки

- Успех — `200` (не `201`), `Content-Type: application/json`.
- `shortUrl` всегда строится от домена ссылки (`https://l.demo.test/…`), а не от `Host` запроса:
  запрос на `http://shlink` и на `sl.demo.test` без `domain` даёт ссылку основного домена.
  `domain`, равный основному, в ответе превращается в `null`.
- **Тело принимается и без `Content-Type: application/json`:** JSON без заголовка, с `text/plain`,
  с `; charset=utf-8` — всё работает. Работает и обычная форма
  (`application/x-www-form-urlencoded`: `longUrl=…&tags[]=…&findIfExists=true`). Неизвестные поля
  не мешают.
- **Проверка `longUrl` очень мягкая** — достаточно «что-то, двоеточие, что-то»: проходят
  `tg://…`, `mailto:…` и даже `текст: …`. Адрес без схемы, пустой, `null`, список → `400`.
  Пробелы по краям не обрезаются. Адрес в 3000 знаков принимается.
- **Даты** (`validSince`, `validUntil`): понимаются смещение (`+05:00`, `-08:00`), `Z`, доли секунды
  любой длины (отбрасываются), запись без пояса (считается в поясе сервера), только дата (полночь).
  В ответе — всегда `2099-12-05T05:01:00+00:00`. Срок в прошлом принимается.
- `maxVisits`: `0` и отрицательные **принимаются**; число строкой — тоже; дробное и не число → `400`.
- Логические поля: `"false"`, `0`, `"true"` понимаются; `null` → `400` (а у `title`, `domain`,
  `customSlug`, `maxVisits`, `shortCodeLength`, дат `null` — то же, что поля нет).
- **Метки** приводятся к виду: без html-разметки, без пробелов по краям, строчными буквами,
  пробелы внутри — дефисами (`"Compat Big Tag"` → `compat-big-tag`). `[]` допустим, `null` и
  строка вместо списка → `400`. В ответе на создание метки идут в порядке запроса, при чтении и
  при возврате существующей ссылки — по алфавиту.
- `title`: пустая строка остаётся пустой строкой; длиннее 512 знаков — обрезается до 512.
- **`customSlug`:** пробелы и `/` заменяются на `-`; регистр сохраняется и важен; допустимы
  кириллица, `_`, `.`, `~`. Занят ли код — проверяется после этой замены и отдельно по каждому
  домену. Занят → `400` (`non-unique-slug`, в теле `customSlug`, для не основного домена ещё и
  `domain`). С `findIfExists=true` и тем же длинным адресом вместо ошибки возвращается сама ссылка.
- **Ошибки** — `application/problem+json`, поля в таком порядке:
  - нет заголовка `X-Api-Key` или он пустой → `401`, `{"expectedHeaders":["X-Api-Key"],"title":"Invalid authorization","type":"https://shlink.io/api/error/missing-authentication","status":401,"detail":…}`;
  - ключ неверный → `401`, `{"title":"Invalid API key","type":"https://shlink.io/api/error/invalid-api-key",…}`;
  - неверное поле → `400`, `{"invalidElements":["shortCodeLength"],"title":"Invalid data","type":"https://shlink.io/api/error/invalid-data","status":400,"detail":"Provided data is not valid"}`;
    пустое тело, `{}` и JSON-список — та же ошибка про `longUrl`;
  - битый JSON → `400`, `type` — `…/malformed-request-body`.

  Ключ проверяется раньше данных: без ключа и с пустым `longUrl` будет `401`.

### Чтение ссылки

- Найдена → `200` и тот же объект, что при создании. Истёкшая и ещё не начавшаяся ссылка читаются.
- Не найдена → `404`: `{"shortCode":"…","title":"Short URL not found","type":"https://shlink.io/api/error/short-url-not-found","status":404,"detail":"No URL found with short code \"…\""}`;
  если прислан не основной `domain`, в теле есть ещё поле `domain`, а в `detail` — `for domain "…"`.
- Ссылка второго домена читается только с `?domain=sl.demo.test`; `Host` запроса на это не влияет.
  Ссылка основного домена с `?domain=sl.demo.test` — **не найдена** (при переходе правило мягче).
- `HEAD` → `200` с пустым телом. Косая черта в конце (`…/код/`) → `404`.

### Служебное

- `GET /rest/health` → `200`, `Content-Type: application/health+json`,
  `{"status":"pass","version":"5.1.8","links":{"about":"https://shlink.io","project":"https://github.com/shlinkio/shlink"}}`
  (версия в эталоне заменена на `<version>` — проверяется только её вид).
- `GET /favicon.ico` → `200`, `image/vnd.microsoft.icon` (сама картинка не сравнивается).
- Неизвестный адрес под `/rest/v3/` → `404` в `problem+json` c `detail` вида
  `Cannot GET http://l.demo.test/v3/…!` (сверяется только вид). `/rest` без ключа → `401`.
- `OPTIONS /rest/v3/short-urls` → `204` с `Access-Control-Allow-Origin: *`,
  `Access-Control-Allow-Methods: GET,POST`, `Access-Control-Max-Age: 3600`, `Allow: GET,POST`,
  а `Access-Control-Allow-Headers` повторяет запрошенные заголовки.
- В каждом ответе есть `X-Request-Id` со случайным uuid («мягкий» заголовок).
- JSON Shlink пишет с `\uXXXX` для не-латиницы и для `< > & ' "`, косую черту не экранирует.
  Прогон это не сверяет: клиенты разбирают JSON, а не читают его как текст.

### Ошибки самого Shlink — в эталон не вошли, повторять не нужно

- **Зависание на новой метке или новом домене.** Впервые встретив метку (или домен) в запросе
  создания, Shlink ставит на неё блокировку и снимает её только при первом запросе рабочего
  процесса; дальше блокировка остаётся висеть, и следующий запрос с той же меткой ждёт бесконечно
  (пока рабочий процесс не перезапустится — раз в 250 запросов). Причина: снятие блокировки
  привязано к объекту связи с базой, а он пересоздаётся после каждого запроса. Для уже
  существующих меток блокировка снимается сразу, поэтому в бою это почти не видно. На стенде это
  обойдено: метки и домены заводятся заранее (`seed-*.txt`).
- `customSlug` со знаками `: ? # [ ] @` → `500` (задумана ошибка проверки, но она не обработана).
  В `tiny` разумно отвечать `400`.
- `customSlug: ""` создаёт ссылку с **пустым кодом** (`shortUrl` — `https://l.demo.test/`).
- Дата, которую не удалось разобрать (`"завтра"`), → `500`; пустая строка вместо даты — «сейчас».
- Тело `null` или JSON-строка → `500`.
- Одна метка дважды в одном запросе — в ответе `tags` приходит не списком, а объектом с номерами
  (`{"0":"a","2":"b"}`).
- `longUrl` числом (`12345`) принимается и сохраняется как строка.

## Что не покрыто

- Поведение при настройках, отличных от стенда (в первую очередь `TIMEZONE` и
  `AUTO_RESOLVE_TITLES` — см. пункты 1 и 7 выше).
- Запросы конкретных клиентов не воспроизводятся; покрыты все поля создания и разные виды тела запроса.
- Заголовки запроса от прокси (`X-Forwarded-*`) и работа за ingress.
- Коды длиной меньше 4 знаков, уже лежащие в базе, и столкновение случайных кодов.
- Нагрузка и одновременные запросы: сценарии идут строго по одному.
