# shlink-import — перенос ссылок из Shlink в tiny

Разовый инструмент: читает все короткие ссылки из базы Shlink 5.1.8 (Postgres) и кладёт их в таблицу
`link` базы tiny. К самому сервису tiny и к Shlink не обращается — работает только с двумя базами.

Главные свойства:

- **из базы Shlink только читает** — соединение помечено «только чтение», каждый запрос идёт в
  транзакции «только чтение»; испортить Shlink инструментом нельзя;
- **повторный запуск безопасен** — ссылка узнаётся по паре «код + домен»; что уже перенесено, не
  дублируется и не перезаписывается (даже если в tiny её успели поправить);
- **рассчитан на миллионы ссылок** — читает и пишет пачками, память не растёт с числом ссылок
  (замер на стенде: 2 млн ссылок — 2 минуты 13 секунд, ~21 МБ памяти);
- **адреса баз берёт только из переменных окружения** и нигде их не печатает — ни в журнале, ни в
  ошибках.

## Что нужно для запуска

| Переменная | Что это |
|---|---|
| `SRC_DSN` | база Shlink: `postgres://логин:пароль@хост:порт/база` |
| `DST_DSN` | база tiny (в ней уже должна быть таблица `link` — её создаёт сам сервис tiny при первом запуске). Не задан — берётся `PG_DSN`: так инструмент запускают в поде самого сервиса (`./shlink-import` лежит в образе рядом с `./svc`) |
| `SRC_TZ` | часовой пояс, в котором работает Shlink, например `Asia/Almaty` или `UTC` |

Адрес можно задать и в виде `host=… port=… dbname=… user=… password='…'`.

**Источник (база Shlink) может стоять за пулером соединений** (pgbouncer, Odyssey; у управляемых
баз это обычно порт `6432`), в том числе в режиме «соединение на транзакцию». Инструмент к этому
готов: каждый запрос к источнику — отдельная транзакция «только чтение», на само соединение
настроек он не ставит (иначе они могли бы достаться самому Shlink через общее соединение пулера)
и подготовленные запросы на нём не запоминает. Проверено через pgbouncer 1.26 в режиме
`transaction`.

**Приёмник (база tiny) — только напрямую, без пулера**: туда инструмент пишет через временную
таблицу, а она живёт на одном соединении.

Чтобы адрес с паролем не остался в истории команд, вводите его так (zsh):

```bash
read -s "SRC_DSN?SRC_DSN: " && export SRC_DSN
```

```bash
read -s "DST_DSN?DST_DSN: " && export DST_DSN
```

### Как узнать `SRC_TZ` (важно)

Shlink хранит время создания и сроки ссылок **без часового пояса** — просто цифры на часах в том
поясе, в котором он сам работает (его настройка `TIMEZONE`; если её нет — `UTC`). Если указать пояс
неверно, время создания и сроки действия всех ссылок съедут на несколько часов.

Узнать пояс можно двумя способами, лучше обоими:

1. посмотреть переменную `TIMEZONE` у Shlink (в его настройках развёртывания); нет такой
   переменной — значит `UTC`;
2. спросить любую ссылку у самого Shlink (`GET /rest/v3/short-urls/{код}`) и посмотреть на хвост
   поля `dateCreated`: `+05:00` — это `Asia/Almaty`, `+00:00` — это `UTC`.

Пояс задавайте названием (`Asia/Almaty`), а не сдвигом: до 1 марта 2024 года в Алматы было +06, и
по названию старые ссылки пересчитаются правильно.

## Запуск

Из корня проекта:

```bash
go build -o shlink-import ./cmd/shlink-import
```

| Команда | Что делает |
|---|---|
| `./shlink-import -survey` | только обзор базы Shlink: сколько ссылок, по доменам, что не переносится. Ничего не пишет, `DST_DSN` не нужен |
| `./shlink-import -dry-run` | пробный запуск: сколько ссылок было бы перенесено и сколько пропущено. Ничего не пишет |
| `./shlink-import` | перенос всех ссылок |
| `./shlink-import -new` | докачка: только то, что появилось в Shlink после последней перенесённой ссылки |
| `./shlink-import -since 2026-11-25T10:00:00+05:00` | докачка: только ссылки, созданные не раньше указанного момента |
| `./shlink-import -after-id 1234567` | докачка: только ссылки с номером строки в Shlink больше указанного |
| `./shlink-import -verify` | проверка после переноса: число ссылок в обеих базах и сверка 1000 случайных ссылок по всем полям. Ничего не пишет |
| `./shlink-import -verify -verify-all` | то же, но сверяются все ссылки до единой |

`-dry-run` сочетается с любым режимом переноса (например `-new -dry-run`). Остальные флаги
(`-batch`, `-verify-sample`, `-overlap`, `-progress`, `-src-tz`) — в подсказке: `./shlink-import -h`.

Код завершения: `0` — всё хорошо, `1` — ошибка или проверка не пройдена, `2` — неверные параметры.

### Как читать журнал

```
10:40:46 ход: прочитано 225000 из 2000000 (11.2%), записано 225000, пропущено (уже есть) 0, конфликтов 0, осталось 1775000, скорость 14142/с, ещё примерно 2m5s
10:42:43 ИТОГ: прочитано 2000000 из 2000000, записано 2000000, пропущено (уже есть) 0, конфликтов 0, осталось 0; заняло 2m13.113s
```

- **записано** — новые ссылки, появившиеся в tiny;
- **пропущено (уже есть)** — такая ссылка в tiny уже лежит (обычное дело при повторе и докачке);
- **конфликтов** — пара «код + домен» в tiny занята ссылкой с *другим* длинным адресом. Такая ссылка
  не переносится и не затирает существующую; первые 20 кодов печатаются в итоге. Откуда берётся:
  дубль в самой базе Shlink, либо этот код уже успели выдать или поправить в tiny;
- строки **ВНИМАНИЕ** — то, на что стоит посмотреть глазами (см. «Что не переносится»).

Если перенос прервался (обрыв связи, Ctrl+C), просто запустите его ещё раз: всё записанное остаётся,
повтор ничего не дублирует. Чтобы не перечитывать уже пройденное, можно продолжить с места обрыва —
нужный `-after-id` написан в сообщении об ошибке.

## Порядок действий при переключении с Shlink на tiny

Идея: основной перенос идёт заранее, пока Shlink работает как обычно; в момент переключения
остаётся догнать только то, что появилось в Shlink за это время, — это секунды.

**Заранее (за день-два), на боевых базах — ничего не меняет:**

1. `./shlink-import -survey` — посмотреть, что лежит в Shlink. Проверить строки «ВНИМАНИЕ» и список
   доменов: ожидаются «основной домен» и `sl.demo.test`. Если отдельной строкой показан сам
   `l.demo.test` или незнакомый домен — остановиться и разобраться до переноса.
2. `./shlink-import -dry-run` — убедиться, что всё читается и числа сходятся с обзором.

**Ключи API — тоже заранее.** Сам инструмент ключи не переносит. tiny принимает их хешем
(настройка `API_KEY_HASHES`, через запятую) — это ровно то, что Shlink хранит в колонке
`api_keys.key`, поэтому сами ключи никуда переписывать не надо, и клиенты ничего не меняют.
Человек выполняет в базе Shlink запрос и вписывает хеши нужных ключей в настройки tiny:

```sql
select k.id, k.enabled, k.key as hash, count(s.id) as links, max(s.date_created)::date as last_used
from api_keys k left join short_urls s on s.author_api_key_id = k.id
group by k.id, k.enabled, k.key order by k.id;
```

Колонку `name` в запрос не добавлять: у старых ключей в ней лежит сам ключ открытым текстом.
Нужны все ключи, которыми недавно создавали ссылки (`last_used`) — их может быть несколько, у
разных клиентов свой. Пропущенный ключ — его клиент после переключения получит `401`.

**В день переключения:**

3. tiny развёрнут и запущен (он сам создаёт таблицы), но запросы клиентов ещё идут в Shlink.
   До переключения ссылки в tiny никто не создаёт.
4. Основной перенос: `./shlink-import`. Shlink при этом работает, клиенты ничего не замечают.
5. `./shlink-import -verify` — выборочная проверка. Если пишет «нет в приёмнике» про несколько
   ссылок — это те, что появились в Shlink уже после шага 4; их заберёт докачка.
6. Прямо перед переключением: `./shlink-import -new` — догнать накопившееся.
7. Переключить запросы на tiny (имя сервиса `shlink` внутри кластера и домены `l.demo.test`,
   `sl.demo.test` начинают вести в tiny). С этого момента в Shlink новые ссылки не появляются.
8. Сразу после переключения: ещё раз `./shlink-import -new` — забрать то, что успело появиться в
   Shlink между шагами 6 и 7. Это единственное окно, когда свежая ссылка может ненадолго отдавать
   404: от переключения до конца этой команды, несколько секунд.
9. Итоговая проверка: `./shlink-import -verify -verify-all` — должна закончиться строкой
   «ПРОВЕРКА ПРОЙДЕНА». После переключения ссылок в tiny будет больше, чем в Shlink (tiny уже выдаёт
   свои) — это нормально, проверка смотрит, что каждая ссылка Shlink есть в tiny и совпадает.

**Откат.** База Shlink инструментом не меняется, Shlink остаётся как был: достаточно вернуть
запросы обратно на него. Учтите, что ссылки, выданные tiny после переключения, Shlink не знает.

**Shlink не выключайте и не удаляйте несколько дней** — пока не убедитесь, что всё работает.
Если в нём за это время по какой-то причине появились новые ссылки — `./shlink-import -new`.

## Что и как переносится

| В Shlink (`short_urls`) | В tiny (`link`) |
|---|---|
| `short_code` | `short_code` — как есть, с учётом регистра |
| домен (`domain_id` → `domains.authority`) | `domain`; у ссылки основного домена — пустая строка |
| `original_url` | `long_url` — как есть (пробелы, кириллица, любая длина) |
| `title` | `title`; нет названия — пустая строка |
| метки (`short_urls_in_tags` + `tags`) | `tags` — массив, по алфавиту (так их отдаёт и сам Shlink) |
| `valid_since`, `valid_until` | `valid_since`, `valid_until` — пересчитаны в точный момент по `SRC_TZ` |
| `max_visits` | `max_visits` |
| `crawlable`, `forward_query` | `crawlable`, `forward_query` |
| `date_created` | `created_at` и `modified_at` — пересчитаны в точный момент по `SRC_TZ` |

## Что не переносится

- **Счётчики и история посещений** (`visits`, `short_url_visits_counts`, `visit_locations`,
  `orphan_visits_counts`) — tiny посещения не считает. Следствие: если у ссылки в Shlink уже
  исчерпан предел посещений, там она отдаёт 404, а в tiny заработает снова (предел в tiny хранится,
  но не применяется). Сколько таких ссылок — показывает обзор.
- **Правила перенаправления** («на айфоне веди сюда, на андроиде туда») — в tiny их нет; ссылка
  будет вести на свой основной адрес. Обзор показывает, у скольких ссылок они есть.
- **Свои перенаправления доменов** (куда вести с корня домена и с несуществующей ссылки) — в tiny
  их нет. Обзор предупреждает, если они настроены.
- **Ключи API** (`api_keys`, `api_key_roles`) и то, каким ключом создана ссылка — ключи в tiny
  задаются настройкой: `API_KEY_HASHES` (хеши из `api_keys.key`, см. порядок переключения) или
  `API_KEYS` (открытым текстом).
- **Служебные поля**: признак «название подставлено автоматически», откуда ссылка импортирована в
  сам Shlink, хеш длинного адреса.
- **Разница между «названия нет» и «название — пустая строка»**: в tiny это одно и то же значение.
- **Дубли кода в самой базе Shlink.** У ссылок основного домена база Shlink не запрещает два
  одинаковых кода (запрещает только сам Shlink, программно). Если такие нашлись, переносится самая
  ранняя, остальные считаются «конфликтами» и печатаются в итоге.

## Тесты и стенд

Тесты — в `internal/shlinkimport/`, работают на живом стенде в docker (если стенд не поднят,
пропускаются). Стенд — настоящий Shlink 5.1.8 со своей базой и база со схемой tiny:

```bash
docker network create tiny-imp-net
```

```bash
docker run --rm -d --name tiny-imp-shlink-pg --network tiny-imp-net -p 54344:5432 -e POSTGRES_USER=shlink -e POSTGRES_PASSWORD=shlink -e POSTGRES_DB=shlink -e TZ=Asia/Almaty postgres:17
```

```bash
docker run --rm -d --name tiny-imp-pg --network tiny-imp-net -p 54345:5432 -e POSTGRES_USER=tiny -e POSTGRES_PASSWORD=tiny -e POSTGRES_DB=tiny -e TZ=Asia/Almaty postgres:17
```

```bash
docker run --rm -d --name tiny-imp-shlink --network tiny-imp-net -p 18082:8080 -e DEFAULT_DOMAIN=l.demo.test -e IS_HTTPS_ENABLED=true -e DEFAULT_SHORT_CODES_LENGTH=5 -e DISABLE_TRACKING=true -e INITIAL_API_KEY=imp-api-key -e TIMEZONE=Asia/Almaty -e TZ=Asia/Almaty -e DB_DRIVER=postgres -e DB_HOST=tiny-imp-shlink-pg -e DB_PORT=5432 -e DB_NAME=shlink -e DB_USER=shlink -e DB_PASSWORD=shlink shlinkio/shlink:5.1.8-roadrunner
```

```bash
docker exec -i tiny-imp-pg psql -q -U tiny -d tiny < migrations/000001_init.up.sql
```

Наполнить Shlink разными ссылками через его же API (6000 штук — около трёх минут):

```bash
SHLINK_IMPORT_SEED=6000 go test ./internal/shlinkimport/ -run TestSeedStand -v -count=1 -timeout 60m
```

Запустить тесты (наполнение в это время запускать нельзя — тесты считают новые ссылки поштучно):

```bash
go test ./internal/shlinkimport/ -count=1
```

Каждый тест работает в своей отдельной схеме базы-приёмника, а особые случаи (дубли кода, старые
даты, правила перенаправления) — в отдельной схеме базы-источника с таблицами, скопированными с
настоящего Shlink, поэтому тесты не мешают ни друг другу, ни данным стенда.

Наблюдение про сам Shlink 5.1.8: при наполнении в 16 потоков, когда запросы одновременно создавали
ссылки с ещё не существующими метками, он намертво завис (все его обработчики остались ждать с
открытой транзакцией; помог только перезапуск). Причину не разбирали. Поэтому наполнение сначала
заводит все метки по одной и лишь потом идёт в 4 потока — так зависаний не было.
